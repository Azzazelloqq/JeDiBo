# JeDiBo — сетевая игра: проект

Режим «По сети» для Классики: два игрока на разных устройствах, комната по коду/ссылке.
План работ по этапам — [PLAN.md](PLAN.md).

**Выбранный вариант (v1): хост на клиенте.** Создатель комнаты держит «сервер» прямо в своей вкладке,
гость подключается к нему по WebRTC. Своей серверной инфраструктуры нет. Логика комнаты пишется независимо
от платформы, чтобы позже её можно было без переделок перенести на настоящий сервер (§11).

---

## 1. Что уже есть и на что опираемся

- **Движок детерминирован**: `createGame(mode, seed, names)` + поток `Action` через `dispatch()` дают одинаковый
  `GameState` на любой машине. ГСЧ живёт в `state.rng`, в `src/core` нет `Math.random`/`Date`.
- **Всё сериализуемо**: `Action`, `GameState`, `GameEvent` — простой JSON.
- **Вопросы карт** (`state.pending`) — тоже обычные `Action` (`choose`/`skip`) с `by = chooser`, в том числе когда
  отвечает соперник («Двойная смерть», «Девальвация», «Предательство»). Отдельного протокола под карты не нужно.
- **Заготовки**: `net/transport.ts` (`Transport`, `NetMessage`, `stateHash`), `ControllerKind = 'remote'` в `Match`,
  плитка «По сети» в меню (заблокирована).
- **Хостинг клиента** — GitHub Pages (статика).

## 2. Как браузеры соединяются

Вкладка не может слушать порт, поэтому два браузера соединяются только через **WebRTC DataChannel**. Для этого им
нужно один раз обменяться описаниями соединения (SDP) через посредника — **сигналинг**.

- **Сигналинг — PeerJS** (npm `peerjs`) и его бесплатный публичный брокер. Хост регистрируется под id
  `jedibo-<КОД>`, гость подключается к этому id. Через брокер идёт только обмен SDP, игровые данные — напрямую.
  Гарантий доступности у публичного брокера нет; если станет мешать — свой `peerjs-server` (§11).
- **NAT** — бесплатные STUN-серверы (по умолчанию в PeerJS). В строгих NAT (часть мобильных операторов, офисы)
  прямое соединение не установится — нужен TURN-ретранслятор. В v1 его нет: показываем понятную ошибку
  «Не удалось соединиться напрямую» и собираем статистику на тестах. Список ICE-серверов — в конфиге, TURN
  добавляется без правок кода.
- DataChannel — надёжный и упорядоченный (`reliable: true`), сообщения — JSON.

## 3. Архитектура

```
 Вкладка хоста                                                    Вкладка гостя
 ┌──────────────────────────────────────────────┐                 ┌───────────────────────┐
 │ UI ─► Match(seat 0) ◄─► LoopbackTransport     │                 │ UI ─► Match(seat 1)    │
 │                              │                │                 │         │              │
 │                    HostRoom (адаптер)         │   WebRTC        │   PeerTransport        │
 │                      ├ Room (чистая логика) ◄─┼─ DataChannel ──►│   (переподключение,    │
 │                      │  createGame/dispatch   │                 │    heartbeat)          │
 │                      │  часы, лог, места      │                 └───────────────────────┘
 │                      ├ таймеры (setTimeout)   │
 │                      └ sessionStorage (лог)   │        PeerJS-брокер — только обмен SDP
 └──────────────────────────────────────────────┘
```

Хост — такой же клиент, как гость: его `Match` говорит с `Room` через транспорт в памяти и не имеет «особого
доступа». Это держит код клиента одинаковым и делает перенос `Room` на сервер заменой транспорта.

Модули:

```
src/net/
  protocol.ts        типы сообщений ClientMsg / ServerMsg, PROTOCOL_VERSION
  room.ts            Room — чистая логика комнаты (без таймеров, I/O, DOM)
  commit.ts          commit-reveal: hash(payload + salt), проверка
  loopback.ts        LoopbackTransport / LoopbackServer — Room в том же процессе (хост, тесты, netsim)
  peer.ts            PeerJS: HostRoom (Room + DataChannel + таймеры + сохранение) и PeerTransport (гость)
  transport.ts       Transport (уже есть) + события состояния соединения
src/session/match.ts Match получает сетевой режим ввода (§6)
scripts/netsim.ts    два бота играют через LoopbackServer, проверка синхронности
```

`src/core`, `protocol.ts`, `room.ts`, `commit.ts` не импортируют ничего из `ui/render/audio/profile` и не трогают
`window/document` — проверяется отдельной сборкой без `lib: dom`. Это и есть условие будущего переноса на сервер.

## 4. Комната (`Room`)

Чистый класс: на вход — сообщения и «текущее время», на выход — исходящие сообщения и «разбуди меня в момент T».
Адаптер хоста превращает это в рассылку по каналам и `setTimeout`.

```ts
interface RoomData {
  code: string;                       // 5 символов, без 0/O/1/I
  seats: [Seat | null, Seat | null];  // { token, name, avatarSeed, rating, connected, lastSeen }
  seed: number | null;                // после commit-reveal (§5)
  log: Action[];                      // все применённые действия — источник истины
  clocks: { turnLeft: number; total: [number, number]; runningSince: number | null };
  status: 'waiting' | 'seeding' | 'placement' | 'play' | 'over' | 'abandoned';
  rematch: [boolean, boolean];
  // + состояние commit-reveal расстановки и seed
}
```

`GameState` не хранится — восстанавливается переигрыванием `log` с `seed`.

Правила:

- **Места.** Хост — место 0, гость — место 1. Цвета и первый ход решает движок по seed, как офлайн.
  Повторный вход с тем же `token` (в `sessionStorage`) = переподключение; третий клиент — «комната занята».
- **Действия.** `submit(action)`: `Room` подставляет `by = место отправителя`, вызывает `dispatch`. Ошибка →
  `reject` отправителю. Успех → `log.push`, рассылка `action` обоим с `seq`, `hash` и снимком часов.
- **Часы — у `Room`.** Отсчёт для `state.current` при `phase === 'play'`; на истечение `Room` сам применяет
  `timeout`. Клиенты только интерполируют снимки и `timeout` не отправляют. Время считается по разнице
  `Date.now()`, так что троттлинг таймеров фоновой вкладки лишь задерживает срабатывание, но не искажает часы.
- **Сдача** — обычный `resign`.
- **Обрыв связи гостя.** Его часы идут. Не вернулся за `ABANDON_MS` (предложение: 120 с), а сейчас его ход/выбор —
  `Room` применяет `resign` за него («соперник покинул партию»).
- **Обрыв хоста.** Хост — единственная точка отказа. `HostRoom` сохраняет `RoomData` в `sessionStorage` после
  каждого изменения; при перезагрузке вкладки хост поднимает комнату заново под тем же peer id, гость
  переподключается сам. Если хост не вернулся за `ABANDON_MS` — гость получает победу локально
  («хост покинул партию») и это пишется в историю.
- **Реванш.** Оба жмут «Реванш» → новый seed (снова commit-reveal), `log = []`.

## 5. Честность: хост тоже игрок

Хост держит `Room`, значит модифицированный клиент хоста мог бы подглядеть или подкрутить. Закрываем то, что
закрывается дёшево; гость **сам** проверяет всё, что приходит, своим `dispatch`.

- **Seed** — совместный: хост шлёт `commit(sA)`, гость в ответ открыто шлёт `sB`, хост раскрывает `sA`, гость
  проверяет хэш. `seed = mix(sA, sB)`. Хост не может «перебирать» seed: `sB` он узнаёт уже после обязательства.
- **Скрытая расстановка** — оба присылают `commit(layout)`; только когда `Room` получил оба обязательства и
  разослал их, клиенты раскрывают расстановки. `Room` и клиент гостя сверяют раскрытие с обязательством.
  Применяются в порядке 0, 1 (второй `place` запускает партию и тратит ГСЧ — порядок обязан быть каноническим).
  Хост раскрывает до того, как увидит расстановку гостя, поэтому подстроиться не может.
- **Ходы** — гость применяет каждое пришедшее действие своим `dispatch`; недопустимое (`!ok`) или несовпадение
  хэша = «соперник нарушил правила / рассинхрон» (§7).
- **Чему остаётся доверять:** часам хоста и порядку колоды Кармы (оба клиента знают весь `GameState`, изменённый
  клиент может подсмотреть будущие карты). Для дружеских партий по коду это приемлемо; закрывается переносом
  `Room` на сервер и фильтрацией состояния.

## 6. Клиент: `Match` в сетевом режиме

- `MatchConfig.net = { transport, seat }`. Контроллеры: `[seat] = 'human'`, другое — `'remote'`.
- Локальный `submit(a)` не применяется, а уходит в `transport.send({ t: 'submit', action: a, cseq })`;
  ввод блокируется до ответа (`awaitingServer`, как `isBusy`).
- Входящий `action` → та же очередь → `dispatch` → `onEvents`: анимации работают как есть.
- После каждого действия — `stateHash(state) === msg.hash`; иначе `resync` → `{ seed, log }` → пересоздать
  состояние, перерисовать доску без анимаций.
- Часы — из снимков `ClockSnap`, `tick()` только интерполирует. `setPaused` на часы в сети не влияет.
- `reject` → `onError(msg)` (тот же тост).
- `Match.fromLog(seed, names, log)` — восстановление при старте и переподключении.
- Бот и хотсит не меняются: сетевой путь включается только при наличии `cfg.net`.

## 7. Протокол

JSON, одно сообщение — один объект. Версия в `hello`; несовпадение → `error: 'version'` («обновите страницу»).

```ts
// клиент → комната
type ClientMsg =
  | { t: 'hello'; v: number; token: string; name: string; avatarSeed: string; rating: number }
  | { t: 'seedShare'; value: number }                 // гость: sB
  | { t: 'placeCommit'; hash: string }
  | { t: 'placeReveal'; layout: Layout; salt: string }
  | { t: 'submit'; action: Action; cseq: number }      // by игнорируется
  | { t: 'resync' } | { t: 'rematch' } | { t: 'leave' }
  | { t: 'ping'; at: number };

// комната → клиент
type ServerMsg =
  | { t: 'welcome'; seat: PlayerId; code: string; status: RoomStatus; opponent: PeerInfo | null }
  | { t: 'opponent'; info: PeerInfo | null; connected: boolean }
  | { t: 'seedCommit'; hash: string } | { t: 'seedReveal'; value: number; salt: string }
  | { t: 'start'; seed: number; names: [string, string]; log: Action[]; clocks: ClockSnap }
  | { t: 'placeCommits'; hashes: [string, string] }   // после него — раскрывать
  | { t: 'action'; seq: number; action: Action; hash: number; clocks: ClockSnap }
  | { t: 'reject'; cseq: number; error: string }
  | { t: 'error'; code: 'version' | 'full' | 'badMsg' | 'cheat'; text: string }
  | { t: 'pong'; at: number; now: number };

type ClockSnap = { turnLeft: number; total: [number, number]; running: PlayerId | null; now: number };
```

Хэш commit-reveal — SHA-256 (`crypto.subtle`) от `JSON.stringify(payload) + salt`, соль — 16 случайных байт.

`stateHash` сейчас покрывает только часть состояния. Нужен хэш **всего** `GameState` (кладбища, `held`, колода,
эффекты, `pending`) — FNV по `JSON.stringify(state)`.

## 8. Транспорт гостя

`PeerTransport implements Transport`:
- heartbeat `ping` раз в 5 с, нет `pong` 12 с → соединение мёртвое;
- переподключение к тому же peer id с backoff (0.5 → 8 с), на каждом — `hello` с тем же `token`; комната отвечает
  `welcome` + `start` с полным логом;
- `onStatus(cb: (s: 'connecting' | 'open' | 'closed' | 'failed') => void)` — `failed` = ICE не сошёлся
  (нужен TURN), показываем отдельной ошибкой.

## 9. UX

- **Меню → «По сети»** → лобби: «Создать комнату» / «Войти по коду».
- **Хост ждёт**: крупный код, «Скопировать ссылку» (`…/#room=K7QXP` — переход сразу входит), «Отмена».
  Подсказка: «Не закрывайте вкладку — игра идёт через ваш браузер».
- **Соперник найден**: карточка соперника → расстановка. «Соперник расставляется…» / ожидание после «Готово».
- **В партии**: индикатор связи у плашки соперника (онлайн / нет связи + таймер до поражения), блокировка ввода в
  чужой ход, «Соперник выбирает…» для вопросов карт, оверлей «Переподключение…».
- **Итог**: «Реванш» (ждёт второго), «В меню». Причины: сдача, время, покинул партию, нарушение правил.
- Для тестов на этапе 4 — минимальные экраны на текущих компонентах; финальный вид — после редизайна (задача A).

## 10. Профиль и рейтинг

Сетевые партии пишутся в историю с `kind: 'net'` и обновляют локальный Эло по рейтингу соперника из его `hello`
(подделать можно — это дружеский режим).

## 11. Задел на перенос на сервер

Если хост-на-клиенте не устроит (NAT, жульничество, вылеты хоста), тот же `Room` запускается в Cloudflare Durable
Object (или Node + `ws`): пишется адаптер `server/roomDO.ts` (WebSocket ↔ `Room`, `storage` вместо
`sessionStorage`, `setAlarm` вместо `setTimeout`) и `WsTransport` для клиента. Хост становится обычным клиентом.
`Match`, протокол, UI не меняются. Промежуточные шаги, если упрёмся в отдельные проблемы:
свой `peerjs-server` (брокер) и/или TURN-сервер в списке ICE.
