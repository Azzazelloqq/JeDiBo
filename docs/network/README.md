# JeDiBo — сетевая игра: проект

Режим «По сети» для Классики: два игрока на разных устройствах, комната по коду/ссылке.
План работ по этапам — [PLAN.md](PLAN.md).

---

## 1. Что уже есть и на что опираемся

- **Движок детерминирован**: `createGame(mode, seed, names)` + поток `Action` через `dispatch()` дают одинаковый
  `GameState` на любой машине. ГСЧ живёт в `state.rng`, в `src/core` нет `Math.random`/`Date`.
- **Всё сериализуемо**: `Action`, `GameState`, `GameEvent` — простой JSON.
- **Вопросы карт** (`state.pending`) — тоже обычные `Action` (`choose`/`skip`) с `by = chooser`, в том числе когда
  отвечает соперник («Двойная смерть», «Девальвация», «Предательство»). Отдельного протокола под карты не нужно.
- **Заготовки**: `net/transport.ts` (`Transport`, `NetMessage`, `stateHash`), `ControllerKind = 'remote'` в `Match`,
  плитка «По сети» в меню (заблокирована).
- **Хостинг клиента** — GitHub Pages (статика). Значит, любой сервер — отдельная инфраструктура.

## 2. Ключевое решение: тонкий авторитетный сервер вместо чистого p2p

В README заложен p2p-lockstep на WebRTC. Предлагаю заменить его на **авторитетную комнату на сервере**, которая
гоняет **тот же `src/core`**, а клиенты продолжают lockstep-ом проигрывать подтверждённые сервером действия.

| | p2p WebRTC (было в планах) | Комната на сервере (предлагается) |
|---|---|---|
| Сервер | всё равно нужен — сигналинг SDP; для ~10–20 % сетей ещё и TURN | один Worker + Durable Object |
| Порядок действий | два источника, нужны правила разрешения гонок | один источник: сервер нумерует `seq` |
| Скрытая расстановка | commit-reveal (хэш → раскрытие → проверка) | сервер держит расстановки, пока не придут обе |
| Seed (цвета, первый ход, колода) | совместный commit-reveal, иначе хост может «перебирать» seed | генерирует сервер |
| Часы и таймауты | каждый считает сам, спор «у кого кончилось время» | часы на сервере, `timeout` выпускает сервер |
| Читерство невалидными ходами | каждый валидирует, при расхождении — рассинхрон | сервер отклоняет, `dispatch` уже валидирует |
| Переподключение | надо договариваться, кто прав | сервер хранит лог действий → клиент переигрывает с seed |
| Задержка | минимальная | +1 круг до сервера (50–150 мс) — для пошаговой игры незаметно |

Для пошаговой игры WebRTC ничего не даёт, а сложность (NAT, TURN, commit-reveal, спорные часы) — большая.
Движок уже чистый TypeScript без DOM, поэтому сервер получает правила «бесплатно».

**Платформа: Cloudflare Workers + Durable Objects** (одна комната = один DO, WebSocket с hibernation,
бесплатный тариф покрывает прототип). Альтернативы с тем же дизайном: Node + `ws` на любом VPS/Fly.io/Render
(тогда `Room` запускается в обычном процессе). Логика комнаты пишется **независимой от платформы** (§4), так что
выбор хостинга меняет только тонкий адаптер.

> ⚠ Требует решения владельца: аккаунт Cloudflare (или другой хостинг) и домен/поддомен для сервера.

## 3. Архитектура

```
 Клиент A (браузер)                     Сервер (Cloudflare)                   Клиент B
 ┌──────────────────────┐               ┌─────────────────────────────┐       ┌───────────────┐
 │ UI ─► NetMatch       │  submit(a)    │ Worker: /room/:code → DO    │       │  NetMatch     │
 │        │ локальный   │ ────────────► │ RoomDO (адаптер WebSocket)  │       │               │
 │        │ ввод не     │               │   └► Room (чистая логика)   │       │               │
 │        │ применяется │  action(seq)  │        ├ createGame/dispatch│ ────► │ dispatch(a)   │
 │ dispatch(a) ◄─────── │ ◄──────────── │        ├ часы, таймауты     │       │ сверка hash   │
 │ сверка stateHash     │               │        ├ буфер расстановок  │       │               │
 └──────────────────────┘               │        └ лог действий       │       └───────────────┘
                                        └─────────────────────────────┘
```

Модули:

```
src/core/            без изменений по сути; добавляется полный stateHash (см. §6)
src/net/
  protocol.ts        типы сообщений ClientMsg / ServerMsg, PROTOCOL_VERSION
  room.ts            Room — чистая логика комнаты (общая для сервера и тестов)
  transport.ts       Transport (уже есть) + WsTransport (переподключение, heartbeat)
  loopback.ts        LoopbackServer: Room в том же процессе — для тестов и netsim
src/session/
  match.ts           Match получает режим ввода «через сеть» (см. §5)
server/              Cloudflare Worker: index.ts (роутинг), roomDO.ts (адаптер), wrangler.toml
scripts/netsim.ts    два бота играют через LoopbackServer (а опционально — через wrangler dev)
```

`server/` импортирует `src/core` и `src/net/{protocol,room}.ts`. Чтобы это не сломалось, `src/core` и эти два файла
не должны импортировать ничего из `ui/render/audio/profile` и не трогать `window/document` — проверяется отдельной
сборкой сервера в CI (`tsc -p server`).

## 4. Комната (`Room`)

Чистый класс без таймеров и сокетов: на вход — сообщения и «текущее время», на выход — исходящие сообщения и
«разбуди меня в момент T». Адаптер DO превращает это в WebSocket-рассылку и `storage.setAlarm()`.

Состояние комнаты:

```ts
interface RoomData {
  code: string;                       // 5 символов, без 0/O/1/I
  seats: [Seat | null, Seat | null];  // { token, name, avatarSeed, rating, connected, lastSeen }
  seed: number;                       // генерирует сервер при старте
  log: Action[];                      // все применённые действия (источник истины для переподключения)
  pendingPlace: [Action | null, Action | null]; // скрытая расстановка
  clocks: { turnLeft: number; total: [number, number]; runningSince: number | null };
  status: 'waiting' | 'placement' | 'play' | 'over' | 'abandoned';
  rematch: [boolean, boolean];
}
```

`GameState` в хранилище не кладём — он восстанавливается переигрыванием `log` с `seed` (сотни действий — микросекунды).

Правила комнаты:

- **Места.** Создатель — место 0, вошедший по коду — место 1. Кто играет «красными» и кто ходит первым, решает
  движок по seed, как и офлайн. Повторный вход с тем же `token` (лежит в `sessionStorage`) = переподключение на своё
  место; третий клиент — отказ «комната занята» (зрители — позже).
- **Действия.** `submit(action)`: сервер подставляет `by = место отправителя` (клиенту не верим), вызывает
  `dispatch` на своём состоянии. Ошибка → `reject` только отправителю. Успех → `log.push`, рассылка `action`
  обоим с `seq`, `hash` и снимком часов.
- **Скрытая расстановка.** `place` складывается в `pendingPlace`, отправителю — `placeAck`, сопернику — только
  «соперник готов». Когда есть обе — применяются **в порядке 0, 1** (второй `place` запускает партию и тратит ГСЧ,
  порядок обязан быть каноническим) и рассылаются обе сразу.
- **Часы — только на сервере.** Отсчёт идёт для `state.current`, пока `phase === 'play'`. Сервер ставит будильник
  на ближайшее истечение (ход или общее время) и сам применяет `{ type: 'timeout', by, total }` как обычное действие.
  Клиенты свои часы **не** уменьшают сами по себе: показывают интерполяцию от последнего снимка и никогда не
  отправляют `timeout`. Пауза на оверлей Кармы в сети не действует (ход идёт; см. открытые вопросы).
- **Сдача** — обычный `resign`, принимается в любой момент от любого места.
- **Обрыв связи.** Отключённый игрок теряет время своими часами как обычно. Если он не вернулся за
  `ABANDON_MS` (предложение: 120 с) и сейчас его ход или его выбор — сервер применяет `resign` за него с причиной
  «соперник покинул партию». Пока отключён и ход не его — просто ждём.
- **Реванш.** После `over` оба жмут «Реванш» → новый seed, `log = []`, места сохраняются (цвета снова случайны).
- **Срок жизни.** Пустая комната удаляется через 10 мин, завершённая — через 30 мин после ухода обоих.

## 5. Клиент: `Match` в сетевом режиме

Сейчас `Match.submit()` сразу кладёт действие в очередь и вызывает `dispatch`. В сети:

- `MatchConfig.net = { transport, seat }`. Контроллеры: `[seat] = 'human'`, другое — `'remote'`.
- `submit(a)` от локального игрока **не применяется**, а уходит в `transport.send({ t: 'submit', action: a })`.
  UI блокирует ввод до ответа (флаг `awaitingServer`, как `isBusy`) — защита от двойного клика.
- Входящий `action` → в ту же очередь `queue` → `dispatch` → `onEvents` (анимации работают как есть, свои ходы
  анимируются после подтверждения, задержка ~100 мс не заметна на фоне анимации).
- После каждого применённого действия — `stateHash(state) === msg.hash`, иначе **рассинхрон**: запросить
  `resync`, получить `{ seed, log }`, пересоздать состояние, перерисовать доску без анимаций.
- Часы берутся из снимков сервера (`clocks` + `serverNow`), `tick()` только интерполирует для отображения.
  Ветка с `submit({ type: 'timeout' })` в сети отключена.
- Ошибка `reject` → `onError(msg)` (тот же тост, что и сейчас).
- Начало партии: клиент получает `start { seed, names, seat, log }` и создаёт `createGame` с этим seed —
  `Match` нужен конструктор «из seed + лог».
- Офлайн-режимы (бот, хотсит) не меняются: сетевой путь включается только при наличии `cfg.net`.

## 6. Протокол

JSON по WebSocket, одно сообщение — один объект. Версия протокола в `hello`; несовпадение → `error: 'version'`
и сообщение «обновите страницу».

```ts
// клиент → сервер
type ClientMsg =
  | { t: 'hello'; v: number; token: string; name: string; avatarSeed: string; rating: number }
  | { t: 'submit'; action: Action; cseq: number }      // by игнорируется сервером
  | { t: 'resync' }
  | { t: 'rematch' }
  | { t: 'leave' }
  | { t: 'ping'; at: number };

// сервер → клиент
type ServerMsg =
  | { t: 'welcome'; seat: PlayerId; code: string; status: RoomStatus; opponent: PeerInfo | null }
  | { t: 'opponent'; info: PeerInfo | null; connected: boolean }
  | { t: 'start'; seed: number; names: [string, string]; log: Action[]; clocks: ClockSnap }
  | { t: 'placeAck' } | { t: 'opponentPlaced' }
  | { t: 'action'; seq: number; action: Action; hash: number; clocks: ClockSnap }
  | { t: 'reject'; cseq: number; error: string }
  | { t: 'over'; winner: PlayerId | 'draw'; reason: string }
  | { t: 'error'; code: 'version' | 'full' | 'notFound' | 'badMsg'; text: string }
  | { t: 'pong'; at: number; serverNow: number };

type ClockSnap = { turnLeft: number; total: [number, number]; running: PlayerId | null; serverNow: number };
```

`stateHash` сейчас хэширует только часть состояния (rng, ход, фигуры). Для ловли рассинхрона нужен хэш **всего**
`GameState` (кладбища, `held`, колода, эффекты, `pending`) — FNV по `JSON.stringify(state)`; порядок ключей
стабилен, т.к. объекты создаются одним кодом. Стоимость — доли миллисекунды на действие.

Известное ограничение: клиент получает полный `GameState`, включая порядок колоды Кармы и (после старта) всё
прочее. Модифицированный клиент может «подсмотреть» будущие карты. Для дружеских игр по коду это приемлемо;
закрывается позже фильтрацией состояния на сервере (клиент получает события вместо действий) — в планы v1 не входит.

## 7. Клиентский транспорт

`WsTransport implements Transport`:
- URL сервера из `import.meta.env.VITE_NET_URL` (dev — `ws://localhost:8787`, прод — задаётся в CI при сборке Pages).
- Heartbeat `ping` раз в 5 с; нет `pong` 12 с → считаем соединение мёртвым.
- Переподключение с экспоненциальной задержкой (0.5 → 8 с), на каждом — `hello` с тем же `token`; сервер отвечает
  `welcome` + `start` с полным логом → клиент переигрывает и продолжает. UI показывает «Переподключение…».
- `Transport` расширяется событиями состояния соединения: `onStatus(cb: (s: 'connecting' | 'open' | 'closed') => void)`.

## 8. UX

- **Меню → «По сети»** → экран лобби: «Создать комнату» / «Войти по коду» (поле 5 символов).
- **Ожидание**: крупный код, кнопка «Скопировать ссылку» (`…/#room=K7QXP`; переход по ссылке сразу входит в
  комнату), статус «Ждём соперника…», «Отмена».
- **Соперник найден**: карточка соперника (имя, идентикон, рейтинг) → расстановка. Пока соперник не готов —
  «Соперник расставляется…», после своей готовности — ожидание без возможности правки.
- **В партии**: индикатор связи у плашки соперника (онлайн / нет связи с таймером до поражения), ввод заблокирован,
  когда ход соперника; вопросы карт, где выбирает соперник — подсказка «Соперник выбирает…».
- **Итог**: «Реванш» (ждёт согласия второго), «В меню». Причины: сдача, время, покинул партию.
- Визуал экранов — по итогам редизайна (задача A, ветка `redesign`). До его готовности — минимальные экраны на
  текущих компонентах (`slab`, `btn`), потом перекрашиваются.

## 9. Профиль и рейтинг

Профили локальные (`localStorage`), доверенного рейтинга нет. В v1: сетевые партии пишутся в историю с
`kind: 'net'` и обновляют локальный Эло по рейтингу соперника из его `hello` (как с ботом, где рейтинг фиксирован).
Подделать можно — это дружеский режим. Серверный рейтинг и аккаунты — вне v1.

## 10. Безопасность и устойчивость

- Сервер не верит полю `by`, проверяет размер сообщения (≤ 8 КБ) и частоту (≤ 20 сообщений/с на сокет).
- Коды комнат — 5 символов из 30 (~24 млн), подбор ограничивается лимитом создания/входа по IP.
- Имена обрезаются до 24 символов, в UI выводятся только через `textContent`.
- Ошибки в `dispatch` на сервере (исключения) ловятся: комната помечается сломанной, клиентам — `error`, лог
  сохраняется для разбора.

## 11. Открытые вопросы владельцу

1. Хостинг сервера: Cloudflare (предложение) или другой? Нужен аккаунт и (желательно) поддомен.
2. Оверлей Кармы в сети: часы идут (предложение) или ставим общую паузу на N секунд?
3. Время на переподключение до поражения: 120 с — ок?
4. Нужен ли в v1 поиск случайного соперника (очередь) или достаточно комнат по коду (предложение: только код)?
5. Сетевые партии влияют на рейтинг (предложение: да, локально) или нет?
