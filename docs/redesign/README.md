## 1. Что за проект

Это **не Unity**: папка называется `UnityProjects`, но внутри TypeScript + Vite без фреймворков (чистый DOM + canvas + WebGL-фон). Запуск: `npm install`, `npm run dev` → http://localhost:5173. Проверка типов и сборка: `npm run build`. Архитектура описана в `README.md` в корне. Коротко:

- `src/core/*` — движок правил. **Не трогать** в рамках обеих задач (кроме чтения).
- `src/render/*` — программный пиксель-арт: палитра `palette.ts`, процедурные текстуры `pixel.ts`, спрайты `sprites.ts`, карты `cardArt.ts`, фон-шейдер `background.ts`, «сок» `fx.ts`.
- `src/ui/*` — экраны (`screens/*.ts`), каждый экран — функция `(root) => cleanup`, роутер `ui/app.ts` (`go(screen)`), хелперы `ui/dom.ts` (`h()`, `btn()`), карта `ui/card.ts`.
- `src/styles/main.css` — все стили, цвета приходят CSS-переменными из `palette.ts` (`applyCssPalette`).
- `src/profile/profile.ts` — профиль и настройки в `localStorage`.

## 2. Жёсткие правила для обеих задач

1. **Пиксель-арт делается так же, как сейчас.** Всё рисуется кодом в низком разрешении на canvas и масштабируется целым множителем (`image-rendering: pixelated`). Палитра — только из `render/palette.ts`. Никаких размытых растров, сглаженных градиентов поверх пикселей и дробных масштабов. Подробно: скилл `jedibo-pixel-art`.
   Исключения, согласованные с владельцем:
   - **логотип** — сохраняет оригинальную векторную форму (см. §4);
   - **иллюстрации карт** переводятся в пиксель-арт один раз скриптом и кладутся PNG-файлами (это наши ассеты, процедурно их не нарисовать).
   - **вариант «б» (1:1 с референсом)** — его стиль задаёт референс; но и он пиксельный (референс сам пиксельный).
2. **Механику не меняем.** Правила Классики, поле 12×12, 21 фигура (12/6/3), Карма — как в движке. На референсах из другого прототипа поле 10×10 и 14 фигур, режимы «Спорт/Хаос/Спираль», «Блиц», «Стражи», «Идолы» — **этого у нас нет**, берём только UX и вид.
3. Не добавлять пункты меню «Зал и сеть», «Обучение», «Язык». Новых настроек, которых у нас нет, не добавлять (только громкость → слайдер).
4. Язык интерфейса — русский. Шрифты — Google Fonts, подключение в `index.html`.
5. Каждый вариант — полностью рабочий экран с той же функциональностью, а не картинка.
6. После каждой заметной части: `npm run build` без ошибок + визуальная проверка в браузере на 1440×900 и 1920×1080 (скилл `jedibo-ui`, раздел «Проверка»).
7. Вся работа — в ветке `redesign` (у каждого агента своя ветка от неё, результат вливается в `redesign`; `main` не трогать). Коммиты небольшие, по смыслу, на русском.

## 3. Варианты: словарь

Для всех экранов используем одни и те же буквы:

| Буква | Название в свитчере | Что это |
|---|---|---|
| **а** | «Референс · наш стиль» | Раскладка и UX как на референсе, но визуальный язык наш (после задачи A): бетон, плиты, наша палитра, наши шрифты, наш логотип. |
| **б** | «Референс 1:1» | Как на референсе и по раскладке, и по виду: тёмно-сланцевые панели, оранжевые заголовки, бирюзовые тумблеры, синие выбранные кнопки, пиксельный закрученный фон. Контент — наш. |
| **в** | «Текущий» | Существующие экраны в переработанном виде (результат задачи A). Раскладка как сейчас. |

Сколько вариантов у какого экрана:

| Экран | Референс | а | б | в |
|---|---|---|---|---|

| Летопись (вместо «Профиля») | `refs/03–05` | ✔ | ✔ | ✔ (текущий «Профиль») |
| Колода | `refs/06` | ✔ | ✔ | ✔ |

### Темы: вторая ось

Задача A ввела две темы: **тёмную** (по умолчанию, исходный дизайн из `main` в новой системе токенов) и **светлую** (красный акцент на тёплом светлом камне). Тема не зависит от варианта: **каждый вариант каждого экрана существует в обеих темах** (решение владельца, в т.ч. для «б»).

| Вариант | Тёмная | Светлая |
|---|---|---|
| **а** | токены тёмной темы A | токены светлой темы A |
| **б** | как на референсе (он тёмный) | **придумывает агент B**: светлая версия стиля референса — та же раскладка, скругления, бирюза/синий/оранжевый акценты, шрифты, но светлые панели и фон; акценты затемнить до контраста ≥ 4.5:1 |
| **в** | тёмная тема A | светлая тема A |

Тема фиксируется при загрузке страницы (`THEME` в `render/palette.ts`: палитра выбирается до генерации спрайтов), выбор — `?theme=dark|light` или Настройки → «Тема».

## 4. Логотип

Источник: `refs/02-logo-guide.png` (гайд: знак + надпись «JE DI BO», цвет `#FF3600`, варианты на белом, оранжевом, чёрном). Вырезанные прозрачные PNG (460×170, растр со скриншота): `assets/logo/jedibo-logo-{orange,black,white}.png`.

Требования: «вписывается по стилю, но сохраняет оригинальный вид». Решение:
- **Знак** (крест из квадратов, четвертей круга и двух точек) по своей геометрии пиксельный — его делаем SVG-реконструкцией по гайду (точная геометрия, ровные кривые) и отдельно **пиксельной версией** для маленьких размеров (иконки, вкладка, рубашка карты), построенной на сетке модуля.
- **Надпись** «JE DI BO» — SVG-трассировка по гайду (узкий жирный гротеск), без пикселизации и без искажений пропорций.
- «Вписывание» — только окружением: бетонная плита/подложка, жёсткая пиксельная тень (`drop-shadow` со смещением без размытия), лёгкое «покачивание» как у текущего логотипа, допустимые цвета гайда (оранжевый / чёрный / белый). Не перекрашивать в градиенты, не добавлять фаски на сами буквы.
- Положить: `src/assets/logo/` (`jedibo-mark.svg`, `jedibo-wordmark.svg`, `jedibo-logo.svg`) + функция `logoEl(opts)` в `ui/widgets.ts`, которую используют все варианты.
- Favicon — пиксельная версия знака.

> Открытый вопрос к владельцу: есть ли векторный исходник (SVG/AI/PDF) логотипа? Если появится — заменить трассировку на него. До этого работаем с трассировкой.

Логотип делает **задача A** (§A2). Задача B использует `logoEl()`.

## 4а. Утверждённые решения владельца

1. Сначала делаем и утверждаем новый дизайн (A), только потом варианты и свитчер (B). См. §5.
2. «Наш дизайн» в вариантах «а» и «в» = утверждённый дизайн после задачи A.
3. «Летопись» заменяет «Профиль»: имя, аватар, рейтинг и статистика не теряются, переезжают в шапку Летописи.
4. Механику не трогаем; с референсов берём только UX и вид.
5. Две темы (тёмная и светлая) — для всех вариантов, включая «б» (см. §3 «Темы»).

## 5. Порядок работ

Работы идут **последовательно, с точкой утверждения** (решение владельца):

```
A: A1 палитра ── A2 логотип ── A3 фон/ЭЛТ ── A4 компоненты ── A5 экраны ── A6 карты/блик ── A7 громкость
   └─► владелец смотрит и утверждает новый дизайн (правки — в ветке A) ──► merge A в ветку redesign
B: стартует только после merge A в redesign: B1 свитчер ── B2 иллюстрации карт ── B3 эмблемы ── B4 варианты «б» ── B5 варианты «а» ── B6 интеграция ── B7 партия «а» ── B8 правила-анимации
```

- Агент A **не начинает** ничего из задачи B (свитчер, варианты, Летопись, иллюстрации карт).
- Агент A заканчивает отчётом для утверждения: скриншоты до/после (`docs/redesign/result/A/`) и `docs/redesign/HANDOFF.md`. Дальше ждёт правок владельца.
- Агент B запускается от ветки `redesign`, в которой уже утверждённый дизайн A, и стартует с чтения `HANDOFF.md`. Вариант «в» во всех экранах = утверждённый дизайн A; его B не переделывает, только подключает к свитчеру. Если для свитчера нужно поправить файл A — правь аккуратно, без изменения утверждённого вида.
